## 2. 结论摘要

先给结论，再展开细节。

### 2.1 总体判断

这个项目已经不是“一个简单的油猴脚本式字幕替换扩展”，而是一个完成度较高的 Manifest V3 浏览器扩展应用，已经形成了比较完整的产品闭环：

- 内容脚本负责字幕识别、翻译、替换、导航、网页正文替换。
- Background service worker 负责共享状态写入、消息处理和并发串行化。
- React UI 负责 popup / options / overlay 三入口体验。
- 学习状态模块负责生词、复习、streak、反馈回写。
- 词库数据、适应性调优、体验指标和远程测试链路都已成体系。

从“是否能继续演进”的角度看，答案是肯定的；从“当前哪里最阻碍继续演进”的角度看，真正的核心问题已经不再是旧报告里批评的那个 `contentScript.js` God file，而是以下四类结构债：

1. **设置 schema 在多处重复定义，导致一致性成本偏高。**
2. **React 侧 storage 层职责过重，已经成为新的聚合热点。**
3. **部分大文件已经从单点巨石演化为多点大块，边界继续收缩的收益很高。**
4. **MV3 工程化仍停留在“多文件顺序注入 + globalThis 协作”阶段，上限明显。**

### 2.2 本项目当前最值得做的三件事

如果只做三件事，建议按这个顺序：

1. **统一设置 schema 单一事实源**
   - 解决 `sharedSettings.js`、`settings-bridge.ts`、`settings-normalizer.ts` 的重复规范化逻辑。
2. **拆分 React storage 超级模块**
   - 解决 `react-ui/src/lib/storage.ts` 过重导致的演进摩擦。
3. **推动 content script 工程化收口**
   - 利用仓库里已经存在的 `contentScriptBundleSpike.entry.mjs` 试验方向，逐步从 28 个顺序注入文件过渡到更明确的 bundle/entrypoint 架构。

## 3. 项目概况与当前成熟度评估

## 3.1 代码库定位

从 `README.md`、`docs/architecture.md` 和源码可确认，本项目的核心价值不是“翻译字幕”，而是“在视频消费场景下做低打扰、可持续的词汇习得增强”。这决定了它的架构重点不是单次翻译质量，而是以下几个长期能力：

- 字幕场景稳定识别
- 低扰动词汇替换
- 站点兼容与权限边界
- 学习状态持续累积
- 多入口设置一致性
- 用户学习反馈反向调优

这也是为什么项目里会出现：

- `learningState.js`
- `adaptiveTuning.js`
- `experienceMetrics.js`
- `runtimeSettingsSync.js`
- `subtitleNavigation.js`
- `overlay` 相关桥接模块

这些模块不是“附加功能”，而是产品闭环的组成部分。

## 3.2 工程成熟度

从仓库状态看，工程成熟度高于一般个人扩展项目：

- `manifest.json` 使用 Manifest V3
- 权限控制较克制：`activeTab`、`scripting`、`storage`
- 默认 host 权限仅限 Bilibili / YouTube / Bilibili subtitle API
- `optional_host_permissions` 允许用户主动扩展到其它站点
- 测试文件数量约 **91 个**
- CI 覆盖 `lint`、`test`、`test:ui`、`build:extension`、打包检查、Windows smoke
- 提供远程测试机脚本：`scripts/test/*`

这说明当前主要矛盾不是“缺少工程纪律”，而是“架构已经长大，需要第二次收边界”。

## 5. 核心执行链路分析

## 5.1 字幕替换主链路

基于 `docs/architecture.md` 和内容脚本源码，主链路大致如下：

1. `contentScript/index.js` 初始化站点运行时。
2. `contentScript/dom-observer.js` 负责 DOM 变化监听与节流调度。
3. `subtitleParser.js` / 站点适配逻辑提取字幕元素与时间轴状态。
4. `contentScript/translation-pipeline.js` 串联分词、命中、翻译、渲染。
5. `translator.js` 根据词库、设置和学习状态决定哪些词可替换。
6. `renderer.js` 负责字幕 token 到 HTML 的构造。
7. `tooltip.js` 和 `webTextReplacement.js` 负责页面悬浮解释和正文替换增强。

这是当前项目最核心的一条业务主干。它的优点是：

- 分层已经比历史版本清晰得多。
- “解析 -> 翻译 -> 渲染 -> 交互” 已经有基本边界。
- 页面字幕、正文增强、overlay 并不是硬塞在一个文件里。

它的不足是：

- 运行时仍主要依赖多模块在全局环境中的协作。
- 渲染安全模型没有完全统一成 DOM-first。
- 内容脚本入口还承担了不少 orchestration 责任。

## 5.2 设置变更链路

当前设置系统实际上已经是项目里最复杂、也最有价值的内核之一：

1. UI 侧通过 `use-v3-settings.ts` 和 `storage.ts` 读写配置。
2. `settings-bridge.ts` 负责让 React 侧复用扩展侧逻辑，并在桥接失败时 fallback。
3. `sharedSettings.js` 负责 schema 规范化、V2/V3 迁移、profile 合并、global controls 合并。
4. `background-message-handler.js` 通过串行队列提交共享状态写入，避免并发踩踏。

这套机制说明作者已经明确意识到“设置一致性”是跨上下文扩展项目的主风险点。问题不在于没有统一设置模型，而在于：

- **统一设置模型已经长出来了，但它不是唯一事实源。**

## 5.3 学习闭环链路

学习闭环包括：

- 生词命中
- 学习状态更新
- 快速复习
- streak
- adaptive tuning
- experience metrics

这部分是项目区别于普通双语字幕扩展的核心竞争力。`learningState.js` 和 React 端 dashboard / quick review 逻辑表明，这个项目已经具备“从展示工具走向学习工具”的趋势。

因此后续优化不应该削弱这条链路，而应该让这条链路更容易被维护、测试和继续扩展。

## 7. 当前主要结构问题与技术债

## 7.1 P0 级结构问题：设置 schema 多源定义

这是当前最核心的设计债。

### 现状

设置相关逻辑同时分布在：

- `sharedSettings.js`（803 行）
- `react-ui/src/lib/settings-bridge.ts`（595 行）
- `react-ui/src/lib/settings-normalizer.ts`（376 行）

其中 `sharedSettings.js` 已经包含：

- schema 版本
- profile 规范化
- domain rules 规范化
- overlay state 规范化
- legacy payload 升级到 V3
- 运行时生效配置计算

而 React 侧又保留了大量 fallback normalize 逻辑，用于桥接失败时自给自足。

### 根因

根因不是“桥接不好用”，而是：

- 扩展运行时是 JS/global API
- React UI 是 TS/import 体系
- 两边都需要同步理解同一份 schema
- 当前没有真正做到“一个 schema 实现，多端消费”

### 风险

- 新增字段时容易遗漏某一侧 normalize
- fallback 逻辑长期漂移
- 测试会越来越多地验证“桥接是否和 fallback 一致”，而不是验证业务本身
- 设置问题一旦出现，表现层可能非常分散

### 推荐方案

推荐改造成 **单一 schema source + 多端 adapter**：

方案 A（推荐）：

- 用一个独立模块承载 schema、默认值、normalize、migration、derived selectors
- Background、content script、React UI 都直接 import 同一实现
- 对旧的 `window.SharedSettings` 只保留兼容薄封装

优点：

- 根因修复最彻底
- 长期维护成本最低
- 端到端测试更简单

代价：

- 需要处理 MV3 注入和构建兼容
- 需要一次性迁移现有桥接依赖

方案 B（保守）：

- 保留 `sharedSettings.js` 为唯一权威
- React 端删除大部分 fallback，只保留最薄的灾备 normalize

优点：

- 改动较小
- 对现有运行时影响更可控

代价：

- 仍然保留 JS/TS 双体系割裂
- 长期不是最优解

结论：**短期可用 B，长期应落 A。**

## 7.2 P0/P1 级结构问题：React storage 层已经过重

`react-ui/src/lib/storage.ts` 1941 行，当前承担了太多职责：

- settings 读写
- learning summary
- quick review
- site permission
- active tab subtitle status
- active tab subtitle navigation
- export/import
- subscription 管理
- onboarding
- experience metrics
- adaptive tuning

### 问题本质

这不是“一个工具库文件稍大”，而是 **UI 数据访问层已经变成应用服务总线**。

### 风险

- 单文件变更频率高，冲突概率高
- 逻辑测试范围被迫扩大
- 任何一个 API 变更都更容易波及非相关功能
- 后续加入更多 UI surface 或更多学习功能时，会继续向同一文件堆积

### 推荐拆分

建议按领域拆为：

- `storage/settings-storage.ts`
- `storage/learning-storage.ts`
- `storage/tab-runtime.ts`
- `storage/permission-storage.ts`
- `storage/export-import.ts`
- `storage/subscriptions.ts`

保留一个薄的 `storage/index.ts` 作为聚合出口，减少调用方改动面。

## 7.3 P1 级结构问题：大文件从“一个巨石”变成了“多个大块”

当前并非没有拆分，而是拆分还没有进入第二阶段。

### 重点文件

- `learningState.js`
- `translator.js`
- `subtitleParser.js`
- `overlay-entry.tsx`
- `options-main.tsx`

### 这类文件的共同模式

- 同时包含 domain logic、状态组织、视图派生、边界处理
- 改一个点，必须理解一个比较大的上下文
- 已经超出“单一关注点文件”的理想边界

### 优化原则

这里不建议按“行数平均切碎”，而应按业务边界切：

- `learningState.js` 按 “状态规范化 / 队列调度 / streak / 导出结构” 分开
- `translator.js` 按 “词条命中 / 原因解释 / 过滤策略 / token 生成” 分开
- `subtitleParser.js` 按 “站点适配 / timeline cache / visibility heuristics” 分开
- `overlay-entry.tsx` 按 “容器 / dashboard / navigation / review / settings bindings” 分开

## 7.4 P1 级工程问题：content script 仍然依赖 28 个 JS 顺序注入

根据 `manifest.json`，当前 content script 仍然是 **28 个 JS 文件顺序注入**。

### 这带来的问题

- 加载与解析成本偏高
- 依赖顺序隐式化
- 全局命名空间污染风险更高
- 重构时更容易受到“先后加载关系”约束
- 共享模块很难天然收敛到现代模块边界

### 但要注意的事实

这不是“完全没有准备”。仓库里已经有 bundle spike，因此合理方向不是全盘推翻，而是：

- 保留现有运行逻辑
- 逐步把 content runtime 收敛到真正的 entrypoint
- 让 `globalThis` 暴露从“主协作机制”退化为“兼容层”

## 7.5 P1 级安全模型问题：字符串渲染和 DOM-first 渲染并存

当前安全状态比旧报告描述的更好，但还不够统一。

### 当前真实状态

- `renderer.js` 使用 `escapeHtml` 处理 token 字段，再 `element.innerHTML = rendered.html`
- `tooltip.js` 使用 `escapeHtml` 生成内容，再 `tip.innerHTML = renderTooltipContent(wordElement)`
- `webTextReplacement.js` 已经引入：
  - `SAFE_HTML_ELEMENT_TAGS`
  - `SAFE_HTML_ATTRIBUTES`
  - `URL_HTML_ATTRIBUTES`
  - `UNSAFE_URL_PROTOCOLS`
  - `containsUnsafeContent`
  - `createWordElement`
  - `appendRenderedTokens`

这说明项目并不是“裸 `innerHTML` 到处飞”，而是已经处于“半字符串模板、半 DOM 白名单”的过渡状态。

### 真实问题

问题不应表述为“项目存在严重 XSS 漏洞”，更准确的表述是：

- **安全策略没有统一成单一渲染模型。**

### 推荐方向

从长期看，应优先选择：

- 字幕替换与 tooltip 内容都尽量走 DOM API / declarative render
- 只在严格受控的静态模板场景保留 `innerHTML`
- 把“允许哪些 tag / attr / URL protocol”沉淀成统一渲染安全层

## 7.6 P2 级性能问题：DOM 观察策略仍有继续收敛空间

旧报告对 `MutationObserver + 300ms 轮询` 的担忧并非完全失效，但程度需要重估。

### 当前比旧版更好的地方

`contentScript/dom-observer.js` 当前已经有：

- `MUTATION_OBSERVER_THROTTLE_MS`
- `PROCESS_DELAY_MS`
- `scheduleProcess()`
- `startTimelinePolling()`

也就是说，这一块已经不是“无节制的裸轮询”。

### 仍然值得优化的点

- 监听范围是否还可以进一步缩小到更稳定的字幕容器
- 站点级适配是否可以决定“观察模式”
- timeline polling 是否能和视频状态结合得更紧
- 是否有必要引入更明确的 page adapter 生命周期

所以这一项应该视为 **性能与兼容性优化方向**，而不是当前第一优先级缺陷。

## 8. 与历史全量审查报告的对比

## 8.1 已经过时的历史结论

以下历史结论，不能直接沿用：

### 1. “contentScript.js 是唯一核心巨石”

已过时。

原因：

- 当前内容脚本已拆分为多个子模块
- `contentScript/index.js` 仍偏大，但已经不是旧版 `1695 行单文件统管一切`

### 2. “storage queue 缺少超时机制”

已过时。

原因：

- `react-ui/src/lib/storage.ts` 已包含 `STORAGE_MUTATION_TIMEOUT_MS = 10000`
- 已有 `runStorageMutationWithTimeout` / `enqueueStorageMutation`

### 3. “containsUnsafeContent 仅检查 style 和 on*”

已部分过时。

原因：

- `webTextReplacement.js` 已加入 URL 属性与危险协议检查
- 白名单模型比旧报告描述更完整

### 4. “legacy popup/options/overlayPanel 与 React 双轨是主问题”

优先级下降。

原因：

- 当前 manifest 和运行入口已经以 React 产物为主
- 真正更值得优先处理的是 schema 重复和 storage 过重

## 8.2 历史判断中仍然成立的部分

以下方向仍然成立，但要换成新版表述：

- content runtime 工程化仍未完全收口
- DOM 观察与轮询仍值得继续优化
- 安全策略仍应进一步统一
- 大文件仍然是长期维护成本来源

## 9. 开源项目对标分析

本节不做“谁更强”的空泛比较，只看哪些设计点值得借鉴，哪些不适合照搬。

## 9.1 asbplayer

参考链接：[asbplayer 文档](https://docs.asbplayer.dev/)

### 项目定位

asbplayer 的定位与本项目最接近：都是围绕字幕、视频和语言学习闭环构建能力，强调：

- 可选择字幕
- 视频内学习
- 字幕导航
- 与记忆系统联动

### 值得借鉴的设计点

1. **明确把“字幕”视为一等领域对象**
   - 不是简单 DOM 文本替换，而是围绕字幕列表、导航、学习上下文构建交互。
2. **学习闭环和媒体上下文绑定**
   - 本项目已经在这条路上，说明方向是对的。
3. **字幕与学习能力可组合**
   - 适合继续强化“字幕命中 -> 学习状态 -> 复习入口 -> 导出”这一链路。

### 不适合照搬的点

- asbplayer 同时支持流媒体和本地视频文件，本项目当前重点仍是浏览器站点内字幕增强，能力边界不同。
- 本项目更强调“轻量注入、低打扰学习”，不应直接演化成大而全的媒体平台。

### 对本项目的启发

- 继续把字幕导航和学习状态视为核心资产，而不是 UI 附属功能。
- 后续拆分模块时，优先围绕“字幕领域对象”而不是“页面脚本工具函数”组织。

## 9.2 Yomitan

参考链接：[Yomitan Wiki](https://yomitan.wiki/)

### 项目定位

Yomitan 是成熟的浏览器词典/查词扩展，强项在：

- 动态 popup
- 原位解释
- 丰富词典源
- Anki 集成
- 高度可配置

### 值得借鉴的设计点

1. **查词与解释能力是独立核心，不依附具体页面**
   - 本项目可借鉴其“核心领域模块稳定、展示方式可变”的思路。
2. **高配置度需要强 schema 纪律**
   - 这正好映射到本项目当前 schema 多源问题。
3. **词典/学习数据是长期资产**
   - 本项目在学习状态层面与其有天然相通性。

### 不适合照搬的点

- Yomitan 的主要交互是查词弹窗，本项目的主要交互是视频字幕内的被动习得，两者主流程不同。
- 本项目不应为了借鉴 Yomitan 而把 UI 复杂度抬到查词工具级别。

### 对本项目的启发

- 统一 schema 和 typed domain model 应该成为第一优先级。
- tooltip / learning status / exported vocabulary 等领域对象应尽量收敛为稳定 contract。

## 9.3 WXT

参考链接：

- [WXT 首页](https://wxt.dev/)
- [Project Structure](https://wxt.dev/guide/essentials/project-structure)
- [Messaging](https://wxt.dev/guide/essentials/messaging)

### 项目定位

WXT 是现代浏览器扩展工程框架，核心价值不在于“提供 UI”，而在于：

- file-based entrypoints
- 更清晰的项目结构
- 更现代的构建与发布体验
- 更适合大型扩展的模块组织

### 值得借鉴的设计点

1. **入口文件是显式资产，不是隐式顺序拼接**
2. **entrypoints / modules / utils 的职责边界清晰**
3. **对消息通信推荐类型安全封装，而不是只用原生字符串消息**

### 不适合照搬的点

- 直接整仓迁移到 WXT 成本不低。
- 本项目已经有现成构建与 CI，贸然整体迁移收益未必立刻覆盖风险。

### 对本项目的启发

- 不一定要“迁移到 WXT”，但应该吸收它的 **entrypoint-first** 和 **module boundary** 思想。
- 可以先在现有 Vite 体系内模拟 WXT 风格的目录与入口组织。

## 9.4 Plasmo

参考链接：

- [Plasmo 首页](https://docs.plasmo.com/)
- [Content Scripts UI](https://docs.plasmo.com/framework/content-scripts-ui)
- [Messaging API](https://docs.plasmo.com/framework/messaging)

### 项目定位

Plasmo 强在浏览器扩展 UI 工程化，尤其是：

- Content Scripts UI
- Shadow DOM 隔离
- 声明式消息组织

### 值得借鉴的设计点

1. **Content Script UI 与页面样式隔离**
   - Plasmo 的 CSUI 通过 Shadow DOM 挂载 UI，避免页面样式污染扩展 UI。
2. **消息按 handler 组织**
   - 背景消息不是散落字符串，而是更接近声明式 handler。
3. **对多入口 UI 很友好**
   - popup / options / content UI 具备天然架构位置。

### 不适合照搬的点

- 本项目不是从零搭建，直接迁移 Plasmo 也会有较高改造成本。
- Overlay 不是简单按钮或小面板，有自己的交互与状态复杂度，不能以“迁到 Shadow DOM 就万事大吉”的方式理解。

### 对本项目的启发

- Overlay 和页面内 UI 值得考虑进一步走 Shadow DOM 隔离。
- 背景消息可以逐步从字符串常量迁移到更明确的 typed contract。

## 9.5 Pair Translate

参考链接：[Pair Translate 仓库](https://github.com/Cookee24/PairTranslate)

### 项目定位

Pair Translate 属于更偏“沉浸式双语阅读”的扩展，强调原文与译文并存、低打扰阅读体验。

### 值得借鉴的设计点

1. **产品焦点明确**
   - 不试图一次性把所有学习能力塞进同一界面。
2. **围绕阅读体验组织功能**
   - 这提醒本项目：学习能力很重要，但不能让设置和面板复杂度压过观看体验。

### 不适合照搬的点

- 它的主场景是网页阅读，不是视频字幕。
- 本项目的时间轴、subtitle navigation、video state 都是额外复杂度。

### 对本项目的启发

- 在继续增强学习闭环时，要持续约束 UI 复杂度，避免“学习系统越来越完整，但视频内体验越来越重”。

## 10. 面向本项目的优化方案

## 10.1 设计原则

后续优化建议坚持四条原则：

1. **单一事实源**
   - schema、runtime contract、学习状态模型都尽量只定义一次。
2. **领域边界优先于工具边界**
   - 围绕 settings、subtitle、learning、tab runtime、overlay 分层，而不是按“某个大工具文件”堆功能。
3. **兼容式演进**
   - 利用当前已有 bundle spike、React 主入口、SharedSettings 兼容层逐步迁移，不做推翻式重写。
4. **安全模型统一**
   - 渲染方式和可接受 HTML/DOM 能力必须有统一约束。

## 10.2 分优先级的优化清单

### P0：必须优先做

#### P0-1 统一设置 schema

目标：

- 让 settings default / normalize / migrate / derive 只保留一份核心实现。

收益：

- 降低最容易发生跨端漂移的风险。
- 以后扩展 profile、site rules、overlay state 的成本明显下降。

建议产物：

- `src/domain/settings/` 或类似目录
- `schema.ts`
- `normalize.ts`
- `migrate.ts`
- `selectors.ts`

#### P0-2 拆分 React storage 层

目标：

- 把 1941 行超级存储模块切成领域存储模块。

收益：

- 降低 UI 层维护成本。
- 为后续 overlay / popup / options 进一步解耦打基础。

### P1：高收益演进项

#### P1-1 收口 content script entrypoint

目标：

- 从 28 文件顺序注入，逐步收敛到真正的 bundle/entrypoint 组织。

建议路径：

1. 先把 runtime contract 和 shared modules 模块化
2. 在不改 manifest 行为的前提下梳理依赖顺序
3. 让 bundle spike 覆盖更多真实运行链路
4. 最后切换 manifest 注入产物

#### P1-2 统一渲染安全层

目标：

- 让 subtitle render、tooltip render、web text replacement 共享同一安全模型。

建议方向：

- DOM API 优先
- 白名单集中定义
- 明确哪些地方允许字符串模板，哪些完全禁止

#### P1-3 梳理消息契约

当前 `runtimeMessaging.js` 已经比散装 `chrome.runtime.sendMessage` 更好，但仍是：

- `MESSAGE_TYPES` 字符串常量
- 手工对齐 payload
- Background 按 if/else 分派

建议逐步演进为：

- 统一 message name -> request -> response contract
- 运行时校验或编译期类型约束
- handler 列表化，而不是单文件 if/else 扩展

### P2：中期优化项

#### P2-1 引入更明确的 page adapter 模式

将站点差异进一步收敛到：

- subtitle selectors
- timeline extraction
- visibility heuristics
- page-specific observer strategy

这样 `subtitleParser.js` 和 `dom-observer.js` 的后续复杂度会更可控。

#### P2-2 Overlay UI 进一步组件化与隔离

方向包括：

- Shadow DOM 隔离评估
- overlay 容器和业务组件分层
- navigation / review / dashboard 拆开

#### P2-3 学习状态引擎继续按领域切分

目标：

- 降低 `learningState.js` 后续继续膨胀的概率。

## 11. 建议的演进路线图

## 11.1 第一阶段：统一基础模型

建议 1-2 周内完成：

- 统一 settings schema
- 拆 storage.ts
- 补针对 schema 单一事实源的测试

验收标准：

- 新增一个 settings 字段，只需要改一处核心定义
- popup/options/overlay 全部通过同一 normalize 结果消费

## 11.2 第二阶段：收口运行时边界

建议 1-2 周内完成：

- 重整 content runtime 共享模块
- 推进 bundle spike 到接近可替换状态
- 引入更清晰的 message handler 组织

验收标准：

- content runtime 的主要依赖链可被单一入口表达
- manifest 中的脚本清单开始明显收缩，或至少依赖顺序更显式

## 11.3 第三阶段：统一渲染与适配模式

建议 2 周左右完成：

- 统一 DOM render safety layer
- 评估 overlay Shadow DOM
- 建立 page adapter 边界

验收标准：

- 渲染安全策略不再分散在多个模块里各自演化
- 新增站点适配时，主要改动集中在 adapter 层

## 12. 风险、收益与实施成本评估

| 项目 | 收益 | 风险 | 成本 | 结论 |
|---|---|---|---|---|
| 统一 settings schema | 很高 | 中 | 中 | 必做 |
| 拆 storage.ts | 很高 | 低到中 | 中 | 必做 |
| content script bundle 化 | 高 | 中到高 | 中到高 | 分阶段推进 |
| 统一渲染安全层 | 高 | 中 | 中 | 应尽快规划 |
| Shadow DOM overlay | 中 | 中 | 中 | 先做验证再决定 |
| 全量迁移 WXT/Plasmo | 中 | 高 | 高 | 不建议直接做 |

## 13. 最终建议

本项目现在最不需要的是“大重写”，最需要的是 **围绕已有成熟成果做第二次收边界**。

推荐的总体策略是：

1. **保留现有产品闭环和测试体系，不动核心价值。**
2. **优先修复 settings schema 与 storage 聚合问题，这两项是现在最真实的演进阻力。**
3. **把 content script bundle 化当成分阶段工程目标，而不是一次性迁移项目框架。**
4. **吸收 WXT / Plasmo 的设计思想，但不要为了“现代化”而强行整仓迁移。**
5. **把 asbplayer / Yomitan 的经验用于强化领域边界，而不是机械复制产品形态。**

一句话总结：

> 这个项目已经过了“证明能做出来”的阶段，下一步不是加更多功能，而是把设置模型、运行时边界和 UI 数据访问层收紧，给后续两年的持续演进留出空间。
